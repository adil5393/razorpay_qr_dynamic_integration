# Odoo-controlled terminal: inspection and implementation plan

Status: design only. The endpoints and flows described as proposed below are not implemented. Do not deploy this document as a payment integration.

## Current behavior

The staff app authenticates users with signed access and refresh tokens; the existing roles are admin and cashier. Both roles can currently create a fixed-amount, single-use INR QR via POST /api/collections. Cashiers see collections they created; admins can see all collections and administer users and Razorpay settings. The create endpoint calls Razorpay before inserting the collection. If the insert fails after a response, it attempts to close the QR. An ambiguous timeout or process crash can still leave an unrecorded payable QR.

A signed Razorpay webhook is verified over its raw body. Event IDs and payment IDs are recorded uniquely. The handler finds a collection by QR ID or a known payment ID, then fetches the QR and its payments from Razorpay. Only a captured payment for the exact fixed amount in INR is treated as successful. A QR closed with reason paid remains pending until capture is confirmed. Closed/expired statuses come from Razorpay. The public page and staff detail can also poll and reconcile against Razorpay. QR creation alone does not mark a collection paid.

Migration 0002 adds API-client, idempotency, callback outbox and audit tables, but the current server has no API-client authentication, request API, delivery worker or callback retry endpoints. There is no Odoo module in this workspace. Existing backend unit tests use a separate PostgreSQL database whose name ends in _test and fake Razorpay; separate live-server tests exist and must not be pointed at production.

## Proposed changes

1. Add durable Odoo request records keyed by authenticated client, instance/database and request reference, with a fingerprint of all immutable fields. Validate positive integer paise, INR, invoice/customer identity and reference lengths. A repeated identical request returns the same record; a changed payload returns 409. Bind each credential to a permitted Odoo instance and environment. Odoo validates invoice state, company, access, currency and residual before sending the request.
2. Persist a creation claim before calling Razorpay. Serialize competing creators in PostgreSQL. Treat a timeout, process death, malformed response or database failure after the external call as an ambiguous outcome: retain the claim and require administrator investigation, never automatically create another QR. The current Razorpay create wrapper does not provide a documented idempotency guarantee; a local database constraint alone cannot prevent duplicates across this external side effect. Define a safe administrator resolution procedure before enabling retries.
3. Associate the QR with the request and reuse the existing signature verification and authoritative Razorpay reconciliation. Persist an outbox event in the same database transaction as each verified captured payment. Include instance, request reference, invoice identity, amount, currency, QR ID and unique Razorpay payment ID. Handle every captured payment individually and flag unexpected amount or currency for investigation. Expiry and cancellation must reflect Razorpay's actual QR close reason; a failed payment attempt does not necessarily make an active QR unusable.
4. Deliver signed callbacks to a configured, restricted HTTPS destination with durable leases and retries. Do not accept arbitrary callback URLs from a request. Record errors and make failed deliveries visible and safely retryable by admins. The receiver must authenticate signatures, deduplicate by event ID and payment ID, and acknowledge only after its accounting transaction commits. Delivery success alone cannot prove Odoo posted the correct accounting entry; define an acknowledgment containing the Odoo payment ID and persist the mapping. Restrict callback destinations and redirects to prevent server-side request forgery.
5. Replace the cashier dashboard with a polling list of incoming Odoo requests and recently completed payments, and show the selected QR and immutable invoice details. Limit manual QR creation, cancellation and administrative actions in the backend to admins. Preserve existing history for administrators. Roll out the new request path and Odoo changes together before disabling the old cashier workflow.
6. Extend the actual existing Odoo integration once available. For each authorized full or partial request, generate and persist a unique reference; reserve or otherwise control competing requests against the residual. On verified payment, lock and revalidate the intended invoice, company, customer and currency, and use Odoo's normal payment registration and reconciliation mechanisms. Store a unique Razorpay payment ID and the accounting payment link in the same transaction as posting; duplicate callbacks return the existing result. An invoice may be partially paid or in payment until bank reconciliation, depending on Odoo accounting configuration. Never infer payment from a QR or browser callback.

## Verification and release gates

Use mocked Razorpay and callback transports and an isolated PostgreSQL test database. Cover authorization, input validation, duplicate and concurrent requests, changed payloads, ambiguous QR creation, duplicate and out-of-order webhooks, captured amount mismatch, failed payment attempts, partial invoice payments, expiry/cancellation, callback outages, retry and Odoo duplicate-post prevention. Run migrations against a disposable database containing representative historical rows and verify upgrade and rollback. Validate frontend roles and polling. Complete integration tests against the actual Odoo test instance before any production cutover.

Deploy only after review: back up PostgreSQL, build release images, explicitly apply additive migrations, deploy the application and Odoo integration using the existing release procedure, and monitor webhook and callback failures. Roll back application images independently of the additive schema when compatible; do not downgrade a migration containing live data without a verified backup and a reconciliation plan. This document adds no migration or endpoint and makes no deployment changes.
